# CEC for apps, stage 4b: requests, capture, device types (2026-11-14)

**Status: built and host-tested, not run on a board.** Nothing below is a
hardware result. The playback device under it was verified on 2026-11-14
(`2026-11-14-cec-e2e.md`); this stage adds what an app can ask of the other
devices on the bus and what it can watch. The bench steps at the end say what
to run and what a pass looks like.

## What was built

- `bsp/cec/cec.h`, `cec.c`: one request at a time, started by a
  `cec_request_*()` call and taken with `cec_request_result()`: raw frames
  with an awaited answer (none, the standard's pairing, or a given opcode),
  power status, system information (physical address, device type, CEC
  version, vendor ID, the TV's menu language), the OSD name of another
  device, renaming this board and telling the TV, OSD string, volume up, down
  and mute to the TV or the audio system, a remote key with hold, request
  active source, set stream path, menu request, `<Abort>`, `<Feature Abort>`,
  vendor commands with and without ID, bus scan (`cec_scan_entry()`).
  A capture (`cec_capture()`, `cec_next_frame()`): this board's frames or
  every frame on the cable (the engine's monitor-all), polls included, with a
  timestamp, the acknowledge and whether this board sent it. A second device
  type (`cec_set_device_types()`), a settable vendor ID, the logical address
  mask, five more events (menu request, menu language, deck play, deck
  control, feature abort) and `from`/`to` on every event. Name lookups.
- `bsp/cec/cec_control.{h,cpp}`: the request layer, pure (no SDK, no clock):
  chained exchanges (frame, send result, awaited answer), the 4 s send and
  1 s answer limits, the step logic of system information, held keys (a
  press every 400 ms, the release at the end of the hold), volume (press and
  release, 300 ms apart, stopping at the first press not acknowledged) and
  the bus scan (the core's scan), and the 32-frame capture ring. Request
  frames go through the same send queue as the device's, marked so their
  results reach the request and not the device (as the stock firmware's raw
  send does).
- `bsp/cec/cec_engine.{h,cpp}`: device init with the vendor ID and two device
  types, name and vendor ID changes on the running device, the claim-over
  flag, the wire's monitor-all, the new event types, name lookups.
- `apps/hello_cec` v002: eight pages stepped with GREY, each request
  printing its result with PASS or FAIL on the LCD and over RTT.
- Host tests: `tests/test_cec_control.c` (new: every request function,
  answered, refused, unanswered, not acknowledged and timed out; the bus scan
  over a scripted bus; the capture modes and overflow), `tests/test_cec_engine.c`
  (extended: two device types with keys to the second address, vendor ID and
  name changes, the new events, names).

## What rests on what

| Claim | Basis |
|---|---|
| Frames, answers and time limits of each request | Host tests against the harvested core's builders and answer matcher; the same matcher the stock firmware's CEC menu uses |
| The bus scan's questions and parsing | The core's scan, host-tested here and in the ported core tests |
| Monitor-all hands every frame on the cable over | The bit engine's own host tests (ported); not run with this BSP |
| A TV answers each request as the docs say | The standard and the stock firmware's menu help; not run with this BSP |

**UNVERIFIED HW:**

- Every request on the wire, and every answer from a real TV.
- The capture in `ALL` mode on a real bus, its timestamps (taken in the main
  loop, so up to one loop pass after the frame) and the drop count under load.
- A request's frames sharing the send queue with the device's answers while
  the TV talks to the board.
- The second device type on a real bus: the audio system's claim of address
  5, the TV sending it volume keys (the device refuses System Audio Control,
  so a TV may never do so), a recorder's or tuner's claim.
- Changing the vendor ID or the device types while running (the vendor ID
  applies at once; the device types claim again).
- Interrupt lateness with the capture in `ALL` mode (more frames handed to
  the main loop; the handlers do the same work either way).

## Bench steps (owner)

1. `fw install-app hello_cec.uf2` (or `fw ramrun hello_cec`), TV on input 1
   with CEC on, launch, `fw rtt` (DIAG lines start `hello_cec:`; captured
   frames `cec frame:`).
2. Page 1 DEVICE: as stage 4a (address 4, keys, GREEN wake, RED standby,
   `late aborts 0 PASS`).
3. Page 2 ASK TV: YELLOW `power status: answered PASS` with `power: on`;
   GREEN `system info: answered PASS` with `0.0.0.0 tv`, a version, a vendor
   ID and the menu language; BLUE the TV's name (`refused` is FAIL here and
   is common: note it); RED `rename: sent PASS` (or `refused PASS`), and the
   TV's input list shows "FW2 renamed".
4. Page 3 REMOTE: YELLOW and GREEN change the TV's volume by one step, BLUE
   mutes: each `sent PASS`, `presses acknowledged: 1 of 1`. RED: the TV's
   menu cursor moves up and keeps moving for 1.5 s. Nav up/down chooses the
   audio system (5); with none, `not_acked FAIL` is the right answer.
5. Page 4 ROUTING: YELLOW with the TV on another input: `answered PASS` and
   the source's address; GREEN: the TV switches to this input, `no_answer
   PASS`; BLUE `answered` or `refused PASS`; RED `sent` or `refused PASS`
   ("Hello FW2" on the TV if it takes it).
6. Page 5 ABORT: YELLOW `answered PASS` with a reason; GREEN `sent PASS`;
   BLUE `answered PASS` with the vendor ID frame; RED `sent` or `refused PASS`.
7. Page 6 SCAN: GREEN, a few seconds: `PASS (the TV answered)` and one line
   per device.
8. Page 7 CAPTURE: GREEN to "frames for this board", then "every frame";
   press the TV remote: `0>4` frames, and with other devices on the cable
   their traffic. Yellow lines are frames this board sent.
9. Page 8 ROLES: GREEN turns the audio system on: `held 0030` (4 and 5);
   with the TV's sound set to an external system, press the TV's volume keys
   and look for `key down: volume_up (41) to 5` in the last line. BLUE
   switches the vendor ID to none: with the capture on, a `give_device_vendor_id`
   from the TV is answered by a `feature_abort` (yellow) instead of a
   `device_vendor_id`.
10. Throughout: `late aborts 0`.

## Bench result, 2026-11-16 (owner, Vizio TV, board on the TV's input 4)

Launched from the app list, `hello_cec` page 1 showed `4.0.0.0 firmware` (MAIN printed "Starting
the app; TV address 4.0.0.0 handed over."), the TV showed the bars and its remote moved the box;
Emberward's remote control worked with no input setting changed. Before the hand-over the apps
claimed 1.0.0.0 and the TV kept the remote keys. Volume via CEC: changed the volume on one TV;
the Vizio acknowledged every press and ignored it.
